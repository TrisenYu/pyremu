## 2026-09-30 — 文件系统系统调用的参数校验缺失: 缓冲区过小与目录读完不可区分, 未知标志位被静默接受

### 现象

三类行为在载荷侧都得不到可判定的结果:

- `getdents64` 的缓冲区容纳不下一个目录项时返回 0, 与目录已读完的返回值相同。调用方据此
  结束遍历, 缓冲区过小被当成目录结束, 目录的内容被整体丢弃;
- `faccessat` 的 *mode* 与 *flags*、`fstatat` 的 *flags* 在处理器签名里以 `_mode`/`_flags`
  声明后未被读取, 传入本层无法兑现的标志 (如 `AT_EACCESS` 0x200) 同样返回成功, 载荷无从
  得知该标志未生效;
- 路径取空且带 `AT_EMPTY_PATH` 时按空路径解析并返回 ENOENT, 而该标志的语义是以 *dirfd*
  自身为目标;
- `unlinkat` 的 *flags* 原样转交模块, 传入 `AT_REMOVEDIR` 之外的位同样删除成功, 载荷无从得知
  该请求已被当作不带标志的删除处理。

四项在按模块 ABI 逐项核对系统调用的参数校验时发现, 非运行时暴露。

### 根因

- 模块侧 `getdents` 的循环在写入量为 0 时以 `break` 结束并返回 `Ok(0)`, 该返回值与循环因
  条目穷尽而结束时的返回值相同, 故两种情形在模块的接口上无法区分;
- 运行时侧三个处理器的 *mode* 与 *flags* 参数自声明起就未被使用, 未知位既不校验也不拒绝,
  而 `AT_EMPTY_PATH` 这一位本应改变目标选取;
- `unlinkat_handler` 同样既不校验 *flags* 也不声明可接受的位, 该位图整体转交模块, 而模块只
  读取其中的 `AT_REMOVEDIR`;
- `read_path` 对非 `AT_FDCWD` 的 *dirfd* 在路径不以 "/" 开头时返回 ENOTDIR, 空路径也被该
  判据拦下, 使按描述符取目标的调用点收不到长度为 0 的路径。

### 修复

- `bsp/sittim/modules/fs/src/ramfs.rs`: `getdents` 在写入量为 0 而当前条目放不下时返回
  `Invalid`, 已经写入过条目时仍按写入量返回; 该函数的文档同步写明这一区分;
- `bsp/sittim/src/syscall/fs.rs`: 新增 `ACCESS_MODE_BITS`、`ACCESS_FLAG_BITS`、
  `STAT_FLAG_BITS` 三张掩码与五个 `AT_*` 常量。`faccessat` 与 `fstatat` 在解引用任何载荷
  指针之前先按掩码校验, 出现掩码之外的位返回 EINVAL, 故非法标志配空结果指针返回 EINVAL
  而非 EFAULT。两个处理器在 *flags* 含 `AT_EMPTY_PATH` 且路径取空时改取 *dirfd* 绑定的
  节点: `fstatat` 直接取该节点的 stat, `faccessat` 以 `stat` 是否成功判定存在性, 描述符
  无效或绑定的是控制台与套接字时返回 EBADF。`getdents_handler` 在缓冲区指针为空而长度
  非 0 时返回 EFAULT; `read_path` 的 ENOTDIR 判据增加长度为 0 的条件;
- `bsp/sittim/src/syscall/fs.rs`: `unlinkat` 在解析路径之前先校验 *flags*, 出现
  `AT_REMOVEDIR` 之外的位返回 EINVAL, 与 Linux `do_unlinkat` 的判据一致; 该函数的文档改为
  写明 *flags* 可接受的位, 以及含该位与不含该位各自要求的目标类型;
- `bsp/sittim/src/ext_mod/vfs_ops.rs`: `VfsOps::getdents` 的文档写明下标无效或缓冲区容纳
  不下一个条目时返回 `Invalid`。

### 回归测试

- `bsp/sittim/tests/syscall_fs_host.rs` 新增四条: `test_getdents_validates_the_buffer`
  (空指针配长度 0 与非 0、长度 23 与 0 容纳不下首条、长度 24 与 40 的写入量),
  `test_faccessat_rejects_unknown_mode_bits_and_flags`、`test_fstatat_rejects_unknown_flags`
  (已接受的位逐一通过, 掩码之外的位返回 EINVAL, 且 EINVAL 先于空结果指针的 EFAULT)、
  `test_empty_path_targets_the_descriptor_itself` (`AT_EMPTY_PATH` 配空路径取到该描述符
  自身的节点与长度, 不带该标志返回 ENOENT, 控制台描述符返回 EBADF),
  `test_unlinkat_rejects_unknown_flags` (`AT_REMOVEDIR` 配未知位 4 与未知高位 `1 << 32` 各返回
  EINVAL, 被拒的调用不改动目录树);
- `bsp/sittim/modules/fs/src/ramfs.rs` 的 `test_getdents_stops_when_the_next_entry_does_not_fit`
  改写为按两次 24 字节读取验证位置推进, 新增
  `test_getdents_reports_invalid_when_one_entry_does_not_fit` (长度 23 与 0 返回 `Invalid`
  且读取位置不变, 随后长度 24 返回 24)。

### 验证

`cargo test --target x86_64-unknown-linux-gnu --test fs_host --test syscall_fs_host`:
37 passed 与 73 passed, 无失败项。

## 2026-09-22 — `Pte::is_leaf()` 不认无权限叶子项: 页表复制把无权限页按页表遍历, 飞地以 S 模式故障冻结

### 现象

回归中 `load stress_ng (exited): PASS` 未出现, 飞地以 S 模式故障冻结, 停在 `fault_halt_exc`。
故障现场为 `scause=0xd` (载入页错误), `sepc=0xffffffe0000042ac` 落在 `copy_table_level` 内;
`stval` 减去 `LINEAR_MAP_OFFSET` 得 `0x839e6000`, 落在 umode 页池区间
`[0x83615000, 0x83A00000)` 内, 是一只普通的 4 KiB 用户页。

### 根因

`mmap(PROT_NONE)` 装入的叶子项是 `V|U` 且 R/W/X 全 0 的编码 (见 `syscall/mmap.rs` 的
`prot_to_pte`), 硬件在末级遇到该编码即报页错误, 这正是 PROT_NONE 的语义。`Pte::is_leaf()`
原按 R/W/X 任一置位判定叶子, 于是把该编码判为指向下一级页表的指针项;
`copy_table_level` 按页表遍历该用户页, 对其中的项按指针解引用, 触发载入页错误。

### 修复

`bsp/sittim/src/paging.rs` 的 `Pte::is_leaf()` 增加 `PTE_U`: R/W/X 全 0 而带 U 位的项也是
叶子。同时新增 `sfence_vma(vaddr)` 与 `sfence_vma_all()` 两个辅助函数, 替换 `map_page` /
`unmap_page` / `set_leaf_flags` / `split_mega_leaf` / `setup_linear_map` 五处的内联
`asm!("sfence.vma ...")`; 主机目标上没有该指令, 该分支取
`core::sync::atomic::fence(Ordering::SeqCst)`。改动前后 `sittim.bin` 的 sha256 均为
`1c656440965b8ba26333f41d8ddcd75fbd751400e2f71c1f40e4686883267e16`, 即该重构不改变生成代码。

### 回归测试

新增 `bsp/sittim/tests/paging_host.rs`, 按源码包含 `paging.rs`, 并以桩件提供
`context::root_pa`、`csr::read_satp` 与 `mem` 的三个取页函数。`paging.rs` 内新增 `mod tests`
四条用例, 其中 `test_entry_without_access_permission_is_leaf` 断言
`Pte((PTE_V | PTE_U) as u64).is_leaf()` 为真; 修复前该断言为假。主机侧全套
`cargo test --target x86_64-unknown-linux-gnu` 得 36 + 8 + 9 = 53 passed。

## 2026-09-22 — sittim 的 mprotect 归入「跳过」分支: musl 线程栈保持无权限编码, 线程首次写入即触发存储页错误

### 现象

回归中 `load malloc_churn p=1` 与 `p=2` 两行均以 `(exited-err code=0)` 失败。t-test1 连
`n-parallel=1` 也经 `pthread_create` 建立线程 (`t-test1.c:625`), 故该失败与并发规模无关,
是线程创建本身失败。

### 根因

musl 取得线程栈分两步: 先以 `mmap(PROT_NONE)` 保留地址区间, 再以
`mprotect(PROT_READ | PROT_WRITE)` 赋予访问权限。sittim 的系统调用分发表把 `mprotect (226)`
归入「跳过 (无副作用)」分支, 只返回 0 而不改写任何页表项。线程栈因而在页表中始终是 R/W/X
全 0 的无权限叶子项, 线程首次写入线程控制块即触发存储页错误, 进程以 SIGSEGV 终止。

### 修复

`bsp/sittim/src/syscall/mmap.rs` 新增 `mprotect_handler`, 并在分发表中接上 226。粒度跟随
页表叶子层级: 4 KiB 叶子就地改写标志位; 2 MiB 超页在请求区间覆盖整张超页时就地改写, 只
覆盖一部分时先经 `paging::split_mega_leaf` 拆成 4 KiB 叶子再逐页改写; 区间内存在未映射的
地址时返回 `ENOMEM`, 参数不合法时返回 `EINVAL`。

### 回归测试

`mprotect` 改写真实页表, 需要页表根与 S 模式页池, 主机侧两者都没有, 故该修复没有可在主机上
执行的用例; 其端到端验证是 root 侧 `regress.sh` 的
`load malloc_churn p=1 (exited): PASS` 与 `p=2 (exited): PASS`。

## 2026-09-22 — 加速执行引擎的 TLB 查询为全表线性扫描: Sv39 下每指令开销随已占槽位数上升

### 现象

以一个两条指令的定长循环测量每条指令的纳秒数: 循环体为一次访存加一条回边, 自始至终
访问同一页, 故每次查询都命中, 不发生页表遍历。循环之前先依次访问 N 个互异的页, 每页
占用一个槽位, 热点页的翻译因而落在第 N 个槽位之后。改前 Sv39 下每条指令的开销随 N
线性上升, 改后与 N 无关:

| 前导页数 | 改前 Sv39 | 改前超出 Bare | 改后 Sv39 | 改后超出 Bare |
|---|---|---|---|---|
| 0 | 32.64 | 11.12 | 33.51 | 11.95 |
| 32 | 36.40 | 14.88 | 34.44 | 11.95 |
| 64 | 40.78 | 19.24 | 34.59 | 12.06 |
| 128 | 51.51 | 30.10 | 34.72 | 12.16 |
| 192 | 59.77 | 38.95 | 34.66 | 12.11 |
| 224 | 63.14 | 42.15 | 34.70 | 12.14 |
| 248 | 67.05 | 45.81 | 34.37 | 11.81 |
| 252 | 67.58 | 46.06 | 34.33 | 11.79 |

同表各段的 Bare 值在 21.5 至 22.6 之间, 全程不随 N 变化, 故上升的部分全部出自查询本身。

以工作集跨度与地址翻译模式交叉测量的结果同向: 取 L2 容量 64 MiB, 使跨度的变化不落在
二级缓存上, Sv39 与 Bare 的每条指令耗时之比改前随跨度上升到 2.5 并在 TLB 条目数附近
转平, 改后稳定在 1.45 上下:

| 页数 | 改前 Sv39 | 改前 Sv39/Bare | 改后 Sv39 | 改后 Sv39/Bare |
|---|---|---|---|---|
| 1 | 25.82 | 1.43 | 27.17 | 1.42 |
| 256 | 32.05 | 1.74 | 28.71 | 1.44 |
| 512 | 47.35 | 2.52 | 29.17 | 1.47 |
| 1024 | 47.06 | 2.51 | 29.13 | 1.46 |
| 4096 | 53.37 | 2.32 | 31.29 | 1.45 |
| 16384 | 49.21 | 2.51 | 29.33 | 1.47 |

两表各由 /tmp 下的独立脚本测得, 每段运行 2 至 3 秒: `scanprobe.py` 只改变前导页数,
`l2delta.py` 只改变跨度与 `satp`。1 页一行的改后 Sv39 由 25.82 升至 27.17, 同一次运行中
Bare 也由 18.01 升至 19.11, 而该段的循环体与 TLB 无关, 故该差异出自两次运行之间的漂移。

### 根因

`translate.rs` 的两处都在条目数组的全体槽位上线性扫描:

- [tlb_lookup](../../pyremu/_native/cpu/src/translate.rs) 遍历 `0..tlb_sz()`, 即 256 个
  槽位, 命中的槽位越靠后比较次数越多;
- `clock_victim` 在未命中时先遍历 256 个槽位找一个空槽位, 未找到再遍历 256 个槽位找第二
  机会, 合计 512 次比较。两者相加, 每次未命中的比较次数约为已占槽位数的三倍。

`clock_victim` 是「时钟」替换策略中手的位置所对应的实现, 手的位置由 `itlb_hand` /
`dtlb_hand` 两个 `Cell` 承载, 逐条指令递增, 命中路径同样要读它。

### 修复

在既有的条目数组内改用组相联组织, 条目总数不变, 故 [TlbEntry](../../pyremu/_native/cpu/src/state.rs)
与 `HartState` 的布局逐字节不变, 无需同步 FFI 三处。

1. 条目数组按组划分: `TLB_WAYS = 4`, `TLB_SETS = TLB_ENTRIES / TLB_WAYS`, 共 64 组。
   第 s 组的第 w 路位于下标 `s + w * TLB_SETS`。
2. 组号取页号乘以黄金比常量的高位: `(vpn * 0x9E3779B97F4A7C15) >> (64 - log2(TLB_SETS))`。
   **取高位而非低位**: 相邻 2 MiB 大页的页号相差 512, 而 `512 % 64 == 0`, 低位作组号会
   使这些大页全部落入同一组, 组相联退化为容量为 `TLB_WAYS` 的直接映射。
3. 查询只探测该页号所属的一组, 至多 4 次比较; 填入时在该组内选取可逐出的条目 —
   优先空槽位, 其次未被访问的槽位, 全部被访问过时清除访问位后取第 0 路。
4. `itlb_hand` / `dtlb_hand` 两个 `Cell` 与 `tlb_insert` 的 `hand` 参数一并移除。
   `WalkCtx` 是引擎内部结构, 不在 FFI 面上, 该改动不影响 Python 侧。
5. `emu-configs.mk` 的 `TLB_ENTRIES` 经 `makefile` 生成 `configs_gen.rs`、经
   [pyremu/makefile](../../pyremu/makefile) 生成 `configs_gen.py`, 两侧容量取自同一处配置。
   新增三条编译期断言, 使改动该配置而破坏分组时编译失败而不是静默退化: 路数为 2 的整数
   次幂、条目数为 2 的整数次幂、条目数不小于路数。

### 回归测试

[tests](../../pyremu/_native/cpu/src/translate.rs) 模块内新增与改写五条, 均以 `cargo test
--manifest-path pyremu/_native/Cargo.toml` 运行:

- `tlb_hit_always_lies_in_own_set`: 按组优先的顺序填满全表, 断言每一组每一路填入后的下标
  都与该页号所属的组一致。把组号改为恒为 0, 该用例失败。
- `tlb_evicts_within_own_set_only`: 在另一组放置一个条目, 填满目标组后再填入两倍路数的
  条目, 断言目标组内的有效条目恒为 `TLB_WAYS` 且另一组的条目未被逐出。把组号改为恒为 0,
  该用例失败。
- `tlb_set_spreads_consecutive_megapages`: 依次填入 `0x40000 + k * 512` (共 `TLB_SETS`
  个相邻 2 MiB 大页的页号), 断言不同组数大于 `TLB_WAYS`。把组号改为取页号的低位, 该用例
  失败, 该用例即针对上述第 2 点。
- `tlb_dirty_reuse`: 在指定的一组内断言脏条目经 `DirtyReuse` 返回并由同一槽位重用,
  非脏条目经 `Hit` 返回。
- `tlb_lookup_miss` / `tlb_insert_and_lookup` / `test_tlb_flush_all` /
  `test_tlb_flush_vpn`: 随查询与填入的新签名改写。

### 未完成

- 端到端收益未测。本次测量用的是定长循环与合成页表, `fn_apps/bin/Lfunc` 的实际提升未取得

- `TLB_ENTRIES` 由 256 提高后查询仍为定值次数的比较, 但 `HartState` 每批次编组的字节数与
  条目数成正比 (两侧 TLB 各 `TLB_ENTRIES` 条, 每条 40 字节), 提高之前需先分析该开销。

## 2026-09-21 — 加速执行引擎的多 hart 吞吐下降: 共享 mtime 的逐指令取最大值与 MSIP 槽位同处一条缓存行

### 现象

同一固件在加速执行引擎上运行的吞吐随 hart 数下降, 而非上升:

| hart 数 (独占物理核) | 改前总吞吐 | 改后总吞吐 |
|---|---|---|
| 1 | 40.25 M/s | 50.18 M/s |
| 2 | 30.06 M/s | 61.52 M/s |
| 3 | 26.98 M/s | 84.83 M/s |
| 6 | 27.10 M/s | 152.68 M/s |

对照实验: 同机并行启动 4 个各自单 hart 的模拟器进程, 分别绑定到 4 个互异的物理核,
合计 162.82 M/s, 每进程 40.68 M/s — 机器本身按核数成比例扩展, 下降出自引擎内部。

### 根因

两条, 都在每条指令都会到达的跨核写路径上:

其一, `advance_clock_source` 对全部 hart 共用的单一 `mtime` 执行 `fetch_max`, 每条指令一次。
x86 的加锁读改写即使不改变取值, 也要取得该缓存行的独占权, 独占权因此在各 hart 所在核之间
按指令速率转移。把该函数整体编译掉之后, 2 hart 由 28.64 M/s 升至 105.68 M/s, 即 1 hart
53.19 M/s 的 0.99 倍 — 线性度恢复到 1, 确认该写路径是本次下降的全部来源。

其二, `ModuleState::msip_pending` 按 hart 索引逐个元素分配, 相邻 hart 的槽位相距 8 字节而
同处一条缓存行, 而 `sync_msip` 每条指令对自己的槽位执行 `swap`。改为按 64 字节跨步分配后,
2 hart 在 12 轮测量中的中位数由 24.89 M/s 升至 28.64 M/s, 两组结果的四分位区间不重叠。

### 修复

1. [concurrent.rs](../../pyremu/_native/cpu/src/concurrent.rs) `advance_clock_source`:
   取最大值之前先以普通读取取回 `mtime` 当前值, 目标值不超过当前值时跳过。
   `fetch_max` 在目标值不超过当前值时不改变任何值, 故跳过与不跳过逐位等价 —
   不引入每 hart 状态, 不改变函数签名。
2. 同文件新增 `MSIP_PENDING_STRIDE = 8`, `ModuleState::new` 按该跨步分配 `msip_pending`,
   新增 `ConcurrentClintCtx::msip_pending_slot(hart_id)` 统一取址,
   [interrupt/clint.rs](../../pyremu/_native/cpu/src/interrupt/clint.rs) 的置位方
   `clint_write_msip_concurrent` 与读取方 `sync_msip` 均经该访问器取址。
3. `sync_msip` 的同一处槽位操作按同样的方式改为先读后写: 槽位为 0 时跳过 `swap`,
   两条读取之间到达的置位留到下一次调用读取, 延迟一条指令。该处收益较小,
   1 hart 由 49.00 M/s 升至 50.18 M/s。

### 回归测试

- `hart_sched::tests::advance_clock_source_matches_per_instruction_fetch_max`: 按指令逐条
  推进 1024 条, 断言 `mtime` 恒等于 `time_base_val + floor(instr_delta * timebase_hz *
  NS_PER_INSTR / 1e9)`, 覆盖同一 tick 内的重复取值与跨 tick 的取值变化。把跳过条件放宽到

### 变更

`bsp/sittim` 是 `#![no_std] #![no_main]` 裸机二进制, `cargo test` 直接失败: bin 目标含
`#[panic_handler]`, 而测试目标链接的 std 提供同一个 lang item
(`error[E0152]: found duplicate lang item panic_impl`); 越过该项后, bin 的
`global_asm!(include_str!("entry.s"))` 与其余模块里的 `asm!("ecall")`、`csrr` 在
x86_64 目标上产生 31 条编译错误。源文件里的 `#[cfg(test)] mod tests` 只能随 bin 目标
一同编译, 因而不存在只编译其中一部分的途径。

上编译执行。`Cargo.toml` 为 bin 目标声明 `required-features = ["firm"]`, 主机侧不打开该
特性, bin 因此不参与构建; `Makefile` 增 `test` 目标
(`cargo test --target x86_64-unknown-linux-gnu`), 固件构建经 `FIRM_FLAGS` 打开该特性。
本轮引入的这两个源文件不引用任何其它模块, 故只测这两处; 其余模块脱开平台依赖后再补。

### 现象

未观察到。该缺陷当前不产生可见后果: `string::memset` 在 crate 内没有调用者。

### 根因

`bsp/sittim/src/string.rs` 的 `memset()` 把填充字节广播为 64 位常量时只取 4 项:
`b | (b << 8) | (b << 16) | (b << 32)`, 缺 `<< 24`、`<< 40`、`<< 48`、`<< 56`。
填充字节取 0xAA 时该常量为 0x0000_00AA_00AA_AAAA, 故 8 字节写入路径的每 8 字节中,
自 1 起计数的第 4、6、7、8 个字节为 0; 4 字节余数路径写入的 `fill64 as u32` 为
0x00AA_AAAA, 其第 4 个字节为 0。2 字节余数路径取 `fill64 as u16` 与 1 字节路径取 `byte`,
两者不受影响。上游 C 写法为累加式 `fill |= fill << 8; fill |= fill << 16; fill |= fill << 32;`,
每一步都基于前一步的结果。

### 修复

`memset()` 的广播改为 `(byte as u64).wrapping_mul(0x0101_0101_0101_0101)`。

### 回归

`bsp/sittim/src/string.rs` 的 `tests::test_memset_repeats_the_fill_byte_across_the_word`
对长度 4、5、6、7、8、9、15、16、17、23、31、33 断言写入区间内每个字节都等于填充字节。
修复前该用例在长度取 4 处失败并给出 `size=4 写入 [aa, aa, aa, 00]`。
另有两处覆盖长度 0 至 64 的逐值用例 (`test_memset_covers_the_requested_length` 与
`test_memcpy_matches_bytewise_reference`), 断言写入区间之外保持缓冲区初值。

### 验证

`make -C bsp/sittim build` 产出的 `sittim.bin` 在改动前后 sha256 相同
(`7ad0f8fe6c83c256efb07646bfe7468ede7899cb56c4391280d302c0b6c73d43`): `memset` 的调用者
为空, 该改动不进入固件二进制。`make -C bsp/sittim test` 为 9 passed。

## 2026-09-17 — cfrac 无参数启动: 取不到内置合数, 并打印 "(null)"

### 现象

载荷以 `argc=0` 且 `argv=NULL` 被转入飞地时 (宿主不传参数, 回归程序的池填充阶段即
如此), cfrac 打印 `usage: (null) [-dv] [-a aborts ] ...` 并以退出码 1 结束, 而不是

### 根因

1. `progName = *argv` 直接取 `argv[0]`。`argv` 为 NULL 时该取值为空, usage 行的

   剩余参数个数为 -1, 不等于 0: 内置合数分支不可达, 控制流随即被下一行的
   `argc < 1` 判为用法错误, 落入 usage 分支。判据写作 `argc <= 0` 才覆盖该情形。

### 修复

`fn_apps/cfrac/src/cfrac.c`: `progName` 加兜底 (取不到 `argv[0]` 时用 `"cfrac"`);
内置合数分支的判据改为 `argc <= 0`。

### 回归

新增夹具 `fn_apps/cfrac/test/zero_argv_main.c`: 以 `(0, NULL)` 调用载荷的 `main`,

的分解式 (qemu 下约 14 s) 且退出码为 0。修复前该目标实测打印 usage 并以 1 退出。

### 附带改动

回归程序的池填充阶段以 `argc=0` 转入载荷 (见 `test_mem_pool` 的 ENTER 入参), 修复后
cfrac 会在其中分解内置合数, 使该阶段骤慢, 故把 `cfrac` 加入 `tee_ecall_regress.c` 的
`MEM_FILL_SKIP`。正常加载阶段显式传入 `CFRAC_SMOKE_N` 小合数, 不受影响。



## 2026-09-16 — sittim 合成的 auxv 缺程序头表三项: C++ 载荷异常展开退化为 terminate

### 现象

C++ 载荷 (json_cpp) 进入飞地后, 任何一次异常抛出都以 `std::terminate` 收场, 进程以
退出码 134 abort。同源的 C 载荷 (json_calc) 与不抛出的 C++ 路径均正常, 故缺陷只在
"进飞地 + 抛异常" 这一交叉条件下显形。

### 根因

`bsp/sittim/src/main.rs` 的 `setup_musl_stack()` 为载荷合成 musl `_start` 所需的
argc/argv/envp/auxv 布局时, auxv 只给出 AT_NULL / AT_GID / AT_UID / AT_BASE /
AT_ENTRY / AT_PAGESZ, 缺程序头表的三项。

musl 静态链接版的 `dl_iterate_phdr` (vendor/musl/src/ldso/dl_iterate_phdr.c) 以
auxv 的 AT_PHDR / AT_PHENT / AT_PHNUM 为唯一数据源遍历程序头 (静态可执行文件没有
`_DYNAMIC`, 无从经它取程序头表); libunwind 又经 `dl_iterate_phdr` 定位
PT_GNU_EH_FRAME, 才能读到 `.eh_frame_hdr` 里的展开表。三项缺失时遍历到的程序头
为 0 个, libunwind 找不到任何 FDE, `_Unwind_RaiseException` 判定栈已到底,
`__cxa_throw` 随即转为 `std::terminate`。整个链路中 auxv 是唯一断点: 载荷的 ELF
本身含完整的 `.eh_frame_hdr` 与程序头表, 只是运行时没有把位置告诉它。

### 修复

1. `bsp/sittim/src/elf.rs` — `load_elf()` 的返回值由入口地址改为 `PayloadInfo`
   (入口 + `phdr_va` / `phentsize` / `phnum`)。新增 `phdr_va_of()`: 程序头表位于文件
   `[e_phoff, e_phoff + phnum * phentsize)` 区间, 该区间必含于某个 PT_LOAD 段内, 按该
   段的 `p_vaddr` 与 `p_offset` 平移即得其 VA (载荷按链接地址原样加载且未重定位, 故
   平移成立); 无覆盖段时返回 0, 调用方据此跳过填写。
2. `bsp/sittim/src/main.rs` — `setup_musl_stack()` 补写 AT_PHDR / AT_PHENT / AT_PHNUM
   三项。

### 回归

`fn_apps/json_calc/src/main_cpp.cpp` 新增 `unwind_selfcheck()`, 在进入 JSON churn 前
先跑一次: 读 auxv 三项并断言非零, 再做一次 8 层递归抛出与捕获, 同时核对沿途每一层的
局部对象都被析构 (预期 8 + 1 次) —— 只断言"捕获到了"不足以区分"逐层展开"与"跳过整段
栈", 故把析构计数一并锁住。缺陷重现时打印 `json_cpp: FAIL unwinding: auxv lacks
program headers (AT_PHDR=0 AT_PHENT=0 AT_PHNUM=0)`, 修复后打印
`json_cpp: unwinding OK (...)`。

注意: 该自检在 `qemu-riscv64` 直跑时读的是 qemu 提供的 auxv, 恒为通过, 不构成对
sittim 的判别; 判别必须让载荷在飞地内运行。此项验证待重建 rootfs 后随 regress 执行,
预期 UART 出现 `json_cpp: unwinding OK` 且无 `FAIL`。

## 2026-09-15 — DTB 未保留固件映像区: 内核 DMA 覆写内嵌 .sittim, 飞地载荷不可执行

### 现象

`fn_apps` 载荷进入飞地后无任何输出: 串口打印停在 `[regress] opened /dev/tee_enclave`,
`[regress] payload dir ...` 一行从未出现. CREATE 与 ENTER 的 ecall 均正常返回,
飞地入口却立即失去踪迹, 且无任何后续打印 (既不是 suspended 也不是 fault 报告).

### 根因

固件 (custom-opensbi fw_jump) 载入 0x80000000, 其映像尾部内嵌 `.sittim` 飞地运行时
(链接地址 0x100000, 即物理地址 0x80100000, 长度 0x34705). 该物理地址恰好落在固件
自身保护范围的边界之外:

- 固件在根域中注册的 M 模式专用固件内存区只覆盖 `[_fw_start, _fw_end)`, 即链接
  `[0x0, 0x8c000)`; 该尺寸经 `sbi_domain_memregion_init` 向上取整到 2 的幂并对齐
  基地址, 实际落成 `[0x80000000, 0x80100000)`;
- 而 `.sittim` 在链接脚本 (`firmware/fw_base.ldS`) 中排在 `PROVIDE(_fw_end = .)`
  之后, 起点正是 0x80100000 —— 两个区间首尾相接而不重叠.

`PlatformConfig` 的 `reserved_memory_ranges` 默认值又只保留飞地内存池 (0x83000000,
256 MiB), 于是这段既不被固件声明为 M 模式专用、也不被 DTB 声明为保留的区间, 在内核
眼中就是可用内存. 1 MiB (order-8, 1 MiB 对齐) 的 virtio-blk 分配取空闲区间
`[0x80100000, 0x80200000)` 内最低的 1 MiB 对齐块, 恰为 0x80100000.

CREATE 的载荷来源正是固件内的 `.sittim` 副本 (`load_payload_from_low_privilege` 按
`[_sittim_base_addr, _sittim_ed_addr)` 复制). 抓到的覆写写入方:

```
[_ram_write_direct] addr=0x80100000 len=1048576
  Bus.write <- _do_read <- _process_descriptor_chain <- _process_queue
  <- _native_unmarshal_virtio <- _speedup_for_cmd_step
```

即 guest 内核经 virtio-blk 读入 1 MiB 数据, DMA 直落 PA 0x80100000, 覆写了固件映像.
此后 CREATE 复制进池的载荷已是垃圾数据, 飞地入口取指即 InstrAccessFault; 该异常
`medeleg=0` 未委派 S 模式, 上抛 M 模式后静默挂起, 故无任何后续输出.

排除项: 固件内嵌副本与 `bsp/sittim/sittim.bin` 逐字节一致 (214789 字节), 排除构建
产物过期; 故障与 `claim_enclave_for_hart` 引入的 hart 归属改动无关.

### 修复

1. `emu-configs.mk` — 新增固件映像保留区配置 `FW_RESERVED_MEM_BASE` (0x80000000) 与
   `FW_RESERVED_MEM_SIZE` (0x200000, 上界即内核载入地址 FW_JUMP_ADDR=0x80200000).
2. `pyremu/makefile` — 将上述两项写入生成的 `pyremu/configs_gen.py`.
3. `pyremu/platform.py` — `reserved_memory_ranges` 默认值改为 [固件映像区, 飞地池],
   DTB 据此生成两个 no-map 节点, 内核线性映射不再包含固件映像.
4. 固件侧 (custom-opensbi) — 新增 `reserve_sittim_memregion()`
   (`lib/enclave_ext/enclave_mem_state.c`, 声明于 `include/enclave_ext/mem_man.h`),
   在 `sbi_init()` 中 `sbi_domain_finalize()` 之前调用: 把 `[_sittim_base_addr,
   _sittim_ed_addr)` 以 `sbi_domain_root_add_memrange(..., align = 0x40000,
   M_READABLE | M_WRITABLE)` 注册为根域的 M 模式专用区域.

第 4 项针对的是第 3 项封不住的第二个缺口. DTB 保留只约束内核的线性映射与分配器, 但
未被任何域覆盖的内存在 PMP 下默认允许 S/U 读写执行: 宿主内核可以直接改写飞地运行时
代码, CREATE 复制进池的载荷即是被改写后的数据. 声明为 M 模式专用后, 该区段经
`sbi_domain_get_oldpmp_flags` 得到 pmp_flags = 0 (本平台无 mseccfg, 只读 SU 位),
S/U 访存被 PMP 拒绝而 M 模式照常绕过; 同时 `fdt_reserved_memory_fixup` 只把不含 S/U
权限的区域写进设备树 `/reserved-memory`, 故该声明使固件自身也向内核宣告此区段保留,
不依赖 pyremu 侧的 `reserved_memory_ranges` 是否与之同步.

区段尺寸 0x34705 被取整到 `[0x80100000, 0x80140000)` (order 18); align 取 0x40000
(256 KiB) 使区段保持单一条目.

## 2026-09-14 — IMSIC `eip` 实时写穿: AIA 模式的输入投递延迟与 legacy PLIC 持平

### 现象

AIA 模式下交互式控制台的输入延迟显著高于 legacy PLIC: 单字符回显延迟中位约
398 ms (最大 2804 ms), 24 字符突发中位约 1067 ms; ctrl+u / ctrl+w 这类多字节编辑
与快速连续输入卡顿明显。

### 根因

`sync_ext_irq_mip` 在 IMSIC 独占外部中断线路 (`eidelivery` 非 0) 时刻意跳过
SEIP/MEIP 的置位, 以避免无条件置位造成的约 22 倍指令吞吐回归 (guest 取到空的
`stopi` 身份后 SEI 与 sret 往返)。代价是: 引擎只能读到 marshal 时刻的 `eip`
快照, 而设备线程在轮内注入的 `eip` 新增位 (RX daemon -> APLIC ->
`IMSIC.set_ip_number`) 要到轮边界 `_native_sync_plic_mip` 才可见, 轮内投递不成立;
同时 WFI 唤醒判定的 `ext_irq_pending` 与 SEIP 的实际置位脱节, hart 被唤醒后看不到
SEIP, 只能空转直到本轮以别的原因为结束。

### 修复

1. `pyremu/interrupt/imsic.py` — 新增 `bind_ffi_states` 与 `_publish_eip`:
   `set_ip_number` / `clear_ip_number` 改动 `eip` 后即时写穿到加速引擎正在使用的
   共享 ctypes hart 状态数组。与 PLIC 的 `_ffi_pending` / `_ffi_level` 同一模式,
   未绑定时为 no-op, 纯 Python 路径不受影响。
2. `pyremu/emulator.py` — `_init_for_speedup_lib` 建好 hart 状态数组后调用
   `IMSIC.bind_ffi_states`。
3. `pyremu/_native/cpu/src/interrupt/mod.rs` — `sync_ext_irq_mip` 对 IMSIC 独占的
   线路改为依据 live `eip` 经 `sync_imsic_one` 驱动 MEIP/SEIP, 并以 `eip_ext_any`
   门控: 无待处理外部中断时不做原子读改写, 有待处理时才同步。清除方向由
   `step_interrupts` 的 `eidelivery != 0` 分支承担, 不会残留 SEIP。

只从 `set_ip_number` / `clear_ip_number` 发布是充分的: 这两处是唯一在单轮加速执行
期间发生的 IMSIC 改动 (此时主线程正阻塞在引擎内), 其余改动都发生在引擎停止时,
由轮边界的 `_marshal_imsic` 全量重拷贝覆盖。

### 回归测试

- Rust (`pyremu/_native/cpu/src/interrupt/mod.rs`):
  `ext_irq_drain_delivers_live_imsic_eip_inline` — 置位 `eip` 后 `sync_ext_irq_mip`
  须在同一轮内置 SEIP; 身份取走后 `sync_imsic` 须清除 SEIP (不产生风暴)。
  `ext_irq_drain_leaves_mip_alone_when_imsic_eip_empty` — `eip` 为空时不得清除
  已有的 SEIP。
- Python (`tests/test_interrupt/test_imsic.py::TestImsicFfiWriteThrough`): 写穿到
  绑定数组、清除后重新发布、未绑定时仍为 no-op、`Emulator` 装配后确实完成绑定。

### 端到端验证

进程内测量 (字节 preload 进 UART RX FIFO 至 guest 读走 RXDATA, 绕开 pty 回显链路
的噪声), 同一探针分别驱动 AIA 与 legacy 两套构建:

| 场景 | 构建 | 样本 | 中位 | p90 | 最大 |
|---|---|---|---|---|---|
| 单字符与 23 字符突发交替 | AIA (修复后) | 331 | 11.1 ms | 20.8 ms | 28.8 ms |
| 同上 | legacy PLIC | 331 | 9.9 ms | 18.2 ms | 25.8 ms |
| 追加 400 字节粘贴 | AIA (修复后) | 620 | 28.0 ms | 29.0 ms | 33.6 ms |
| 同上 | legacy PLIC | 620 | 26.9 ms | 28.7 ms | 41.8 ms |

两种口径下 AIA 与 legacy 形状一致, 字节无一丢失, 无秒级离群。pty 回显口径的复测
(同一探针, 同一构建): 单字符中位 398 ms 降至 14 ms (legacy 12 ms), 24 字符突发
中位 1067 ms 降至 182 ms (legacy 125 ms); 该口径受宿主负载影响, 同一二进制的多次
运行之间中位数可相差一个数量级, 故以进程内测量为准。

### 说明

RX 通知退出 (`exit_reason::RX_WAIT`) 予以保留, 但其职责已收窄为「尽快触发
ring buffer 到 UART FIFO 的搬运」— 中断投递本身不再依赖它。相关注释已同步更正。

## 跨 hart 注入的外部 MSI 对属主 hart 不可见: 补齐 IMSIC `eip_ext_any` 缓存

### 现象

AIA 模式 (`eidelivery != 0`, 引擎侧 `CFG_AIA=true`) 下, 经 MMIO 写 `seteipnum` 注入
的外部中断 (设备 MSI, IID 大于等于 6) 会让目标 hart 的 `mip.MEIP/SEIP` 置起, 但该 hart
读 `mtopi` / `stopei` 得到 0 — 即"有中断线、无 identity"的虚假外部中断。S 模式外部中断
handler 读到 STOPEI = 0 后无从认领, 与 `sync_imsic` 的清理分支 (topei 为 0 即清 `SEIP`)
来回抵消, 形成反复进入外部中断的循环。

### 根因

`imsic_topei_peek` 对**外部**中断有一处快速排除条件: `eip_ext_any == 0` 时直接返回 0
(该缓存表示"任一 eip 位非 0", 由 `imsic_update_eip_ext_any` 在 eip 变更后重算)。
设备 MSI 的注入路径 `imsic_handle_seteipnum` 到 `imsic_eip_set` 只置 eip 位与
`mip.MEIP/SEIP`, **不置 `eip_ext_any`**。原注释给出的理由是"属主 hart 会懒刷新,
且 IPI IID 1/3 绕过该快出" — 对 IPI 成立, 对经 MMIO 注入的设备 MSI 不成立:
这类注入可能来自另一个 hart 的加速执行线程, 属主 hart 在此之后不会再重算该缓存。

### 修复

`pyremu/_native/cpu/src/state.rs` 的 `ImsicFile.eip_ext_any` 由 `u8` 改为 `AtomicU8`
(布局不变: 1 字节、对齐 1, 与 Python 侧 `ImsicFileC` 的 `c_uint8` 偏移一致),
`imsic_eip_set` 在置 eip 位的同时以 `fetch_or` 置位该缓存; `imsic_update_eip_ext_any`

## 宿主回归驱动的退出码读取改经 syscall: `(exited-err code=0)` 不再吞掉真实退出码

### 现象

`tee_ecall_regress` 报告载荷自报错误时, 退出码恒为 0。chibicc 载荷实际以 1 退出
(M 模式侧可见 `[dbg-mem-interact] ... term=self-exit exit_code=1`), 宿主侧却打出
`(exited-err code=0)`。状态枚举正确而退出码恒 0, 使失败行看不出真实成因。

### 根因

ENTER / RESUME 的运行状态与退出码打包在同一个 64 位返回值中 (低 32 位为状态枚举,
高 32 位为退出码, 见 `tee_enclave.h` 的 `TEE_RUN_STATE` / `TEE_EXIT_CODE`)。但该驱动
的 ioctl 封装走 libc 的 `ioctl()`, 其原型返回 `int`:

```
extern int ioctl (int __fd, unsigned long int __request, ...);
```

高 32 位在 libc 层被截掉, `TEE_EXIT_CODE(rc)` 因而恒得 0。低 32 位的状态枚举恰好完整,
所以故障表现为 "状态正确、退出码恒 0", 不易被察觉。

### 修复

`bsp/tee_aux_tools/cache-probe-exploit/tee_ecall_regress.c` 的 `do_enter` / `do_resume`
改经 `syscall(SYS_ioctl, ...)` 取原始返回值 (原型为 `extern long int syscall(...)`)。
其余 ioctl (CREATE / SHUTDOWN / GET_MEM) 只读低 32 位的成功或失败语义, 保持不动。

### 回归测试

- 静态: 预处理确认 libc 原型为 `int ioctl(...)` 与 `long int syscall(...)`; 重编后的
  `bin/tee_ecall_regress` 在 ENTER / RESUME 两个读值点均以 `srai a3, a0, 0x20` 取高
  32 位, 即从完整的 64 位返回值中取退出码。修复前该位移作用在被截断的 32 位值上,
  结果恒为 0。
- 端到端: 重新生成 rootfs 镜像后, chibicc 的失败行应由 `(exited-err code=0)` 变为
  `(exited-err code=1)`。

## 飞地时间片耗尽改由 M 模式调度器处理: 长时载荷不再被宿主恢复预算误判为不终止

### 现象

`tee_ecall_regress` 中 ising / json_calc / linalg 三个载荷固定以 `(suspended): FAIL`
收场, 而同一批二进制不经飞地执行时结果正确。回归日志中每个载荷都出现成对的

```
[quota] suspend t=...
[quota] resumed t=...
```

共 21 对, 间隔恒为 10027324 个 tick (恰好一个时间片); 随后宿主驱动打印恢复预算耗尽
并执行 SHUTDOWN, 判定收场为 `(suspended)`。

### 根因

S 模式运行时的时间片耗尽处理只做了一件事: 无条件 SUSPEND, 把 CPU 交还宿主。宿主驱动的
`run_till_norm_done` 在 RESUME 上阻塞, 收到 SUSPEND 便原样再次 RESUME, 于是所谓
"时间片轮转" 退化为 "飞地让出 / 宿主交回" 的往返: 没有任何一方推进载荷进度, 只是消耗
宿主侧的 `RESUME_BUDGET`(64)。预算耗尽后宿主判定该载荷不终止, 主动 SHUTDOWN, 结果被
记为 `(suspended)` FAIL。

时间片本是飞地之间轮转的资源, 交还宿主既无调度意义, 又抹掉了 "载荷仍在推进" 这一事实。

### 修复

S 与 M 两侧各加一个让出原因码, 由 M 模式调度器决定后续处置:

1. `bsp/sittim/src/constants.rs` 与
   `bsp/custom-opensbi/include/enclave_ext/enclave_types.h` — 新增
   `ENCLAVE_SUSPEND_VOLUNTARY = 0` (自愿让出, 必须交还宿主) 与
   `ENCLAVE_SUSPEND_QUOTA = 1` (时间片耗尽, 由调度器决定切换或续期), 两侧数值一一对应。
   SUSPEND 以 a0 承载该原因码。
2. `sittim/src/concurrency/sched.rs` — `tick_and_check_quota` 改以
   `ENCLAVE_SUSPEND_QUOTA` 让出。引导期交接 (`main.rs`) 与线程阻塞让出 (`thread.rs`)
   仍为 VOLUNTARY, 这两处是 "等宿主回话", 必须交还宿主。
3. `custom-opensbi/lib/enclave_ext/ext_ecall.c` — `suspend_enclave_handler` 读取 a0
   分派:
   - QUOTA 且存在其它就绪飞地: 当前飞地置就绪位, 目标飞地清就绪位, 经
     `alter_hart_ctx_for_enclave` 切换, 并把目标 mepc 推过它自己的那条 SUSPEND ecall;
   - QUOTA 且无就绪飞地: 就地续期。此时 mdid / PMP / satp / 全部 GPR 都还在本飞地身上
     (ecall 只是陷入 M 模式), 上下文无需保存与恢复, 只把 mepc 推过 SUSPEND 即返回;
   - VOLUNTARY: 原路交还宿主。
   两条 QUOTA 路径都不经过宿主。
4. `pick_next_quota_ready` (新增) — 就绪飞地选取: 优先级高者优先, 同优先级按
   enclave_id 环形轮转 (先取 id 大于当前飞地的候选, 取不到则回绕到更小者), 无就绪飞地
   返回 `HOST_MDID`。扫描范围自槽位 1 起: 槽 0 是宿主而非候选, 且 `HOST_MDID` 同时是
   "无目标" 的返回值, 二者混同后调用方无法区分 "切给宿主" 与 "没有目标"。
5. 就绪位 `quota_ready` 的生命周期: CREATE 在置 `status = 1` 之前先清零 (槽位可能由已
   终止飞地复用, 残留的 1 会让调度器切换到一个从未 ENTER 过的飞地); RESUME 清零
   (被宿主恢复后即不再处于调度就绪态)。

### 回归测试

飞地调度路径没有 pytest 接缝 (`tests/` 下无对应测试点), 回归见证只能是端到端
`tee_ecall_regress`。判定标准: ising / json_calc / linalg 由 `(suspended): FAIL` 变为
`(exited): PASS`, 且宿主侧不再出现成对的 `[quota] suspend` / `[quota] resumed`。

已完成的验证: `make -C bsp/sittim build` 与 `make build-fw-jump` 均以 0 退出;
`llvm-objdump -d --disassemble-symbols=suspend_enclave_handler` 在部署产物
`build/elf/custom_opensbi_fw_jump.elf` 中可见新分支 (取 a0 的 `ld s1, 0x50(s2)`, 原因码
比较 `li s6, 0x1` 后 `bne s1, s6`)。

端到端: `regress-check load ising` 已由 `(suspended): FAIL` 变为 `(exited): PASS`
(M 模式侧 `term=self-exit exit_code=0`), 且整段 UART 输出中不再出现成对的
`[quota] suspend` / `[quota] resumed`; 同批的 json_calc / linalg 同样转为
`(exited): PASS` (两者的 `exit_code` 均为 0, linalg 自检 `max|x - x_true| = 2.728e-11`)。

### 影响与取舍

就地续期意味着载荷在自行退出或自愿让出之前不再回到宿主, 宿主侧 `RESUME_BUDGET` 因此
不再能约束不终止的载荷。宿主发起的终止仍然有效: `request_shutdown` 经 IPI 送达, S 模式
在中断上下文的 `check_pending_requests` 中响应并退出。切换分支在本项目的驱动模型下暂时
不可达 (宿主阻塞在 RESUME, 同一 hart 上不会出现第二个就绪飞地), 属前瞻性预留。

## 恢复加速引擎的 TermIO RX 通知退出: AIA 模式下键盘输入不再被延迟数秒

### 现象

AIA 模式下引导到 `zsh` 后键盘输入无回显, 交互表现为模拟器长时间不响应; 但 Ctrl+Q
仍能通知调试器暂停被调试程序 (该路径直连停止标志, 不受本缺陷影响)。

### 根因

单个 hart 的加速执行轮次 (`hart_worker`) 原本在指令循环顶部检查 TermIO 的 RX 通知位
(`FfiUartCtx.rx_notify`), 置位时立即结束本轮, 把控制权交回 Python 侧搬运 stdin 字节。
该退出块在 `e904ba4` (WFI/CLINT/AIA 调整) 中被注释掉, 于是通知被完全忽略:

- stdin 新字节由 termio 线程写入进程内的 RX ring buffer 并置位通知位, 字节要到达
  受调试程序还需 Python 侧两步搬运 — RX daemon 把 ring buffer 搬进 UART FIFO, APLIC
  再把中断注入 IMSIC 的 `eip`;
- 这两步都发生在 Python 侧, 单轮加速执行内不可见; 且 IMSIC 独占外部中断线路
  (`eidelivery` 非 0) 时 `sync_ext_irq_mip` 刻意不置 SEIP (无条件置位会造成约 22 倍
  指令吞吐回归), 引擎读到的 `eip` 又只是 marshal 时刻的快照。

三条合起来: 本轮既无法投递中断, 又不会退出, 输入只能等本轮加速执行自然结束才被处理。
交互式控制台下单轮长达数秒 (实测第 2 次输入延迟 8.04 s, 第 3 次延迟 136.8 s), 期间
受调试程序得不到任何键盘字节。

### 修复

1. `pyremu/_native/cpu/src/hart_sched.rs` — 恢复退出块并以 `imsic_owns_ext_line`
   门控: 仅当 IMSIC 存在且 `eidelivery` 非 0 (即外部中断线路由 IMSIC 独占) 时才为
   RX 通知退出本轮; legacy PLIC 模式下 `sync_ext_irq_mip` 已在本轮内联置位 SEIP,
   不退出的旧行为得以保留, 不影响该模式的输入吞吐。
2. `pyremu/_native/cpu/src/state.rs` — 新增退出原因 `exit_reason::RX_WAIT = 9`。
   它不写入 Python 侧停止标志, 调试器不会把它当成暂停事件 (未知退出原因被
   `_native_handle_exit` 忽略); 对应的 Python 常量 `EXIT_RX_WAIT` 加在
   `pyremu/core/hart.py`。
3. `pyremu/emulator.py` — `_speedup_for_cmd_step` 在本轮结束时**无条件**清零
   `_rx_notify` (旧行为是等 ring buffer 与 UART FIFO 皆空才清)。本轮既已结束, 通知
   即已兑现; 若仍按旧条件清理, 在 UART FIFO 已满或受调试程序关中断的窗口内, 下一轮
   会在第一条指令之前立即退出, 受调试程序得不到任何执行机会而活锁 (每轮指令数恒为 0)。
   尚未搬运的字节仍留在 ring buffer, 由每轮 `_feed_uart_stdin` 与 RX daemon 继续搬运。

### 回归测试

`pyremu/_native/cpu/src/concurrent.rs` 新增两个互补的单元测试, 共用
`run_rx_notify_case(imsic_owns)`: 受调试程序在 `jal x0, 0` 无限循环中执行, termio

- `rx_notify_exits_batch_when_imsic_owns_ext_line` — 断言退出原因为 `RX_WAIT` 且本轮
  指令数为 0。修复前实测该断言失败: `left: 8 (TIMEOUT)`, `right: 9 (RX_WAIT)`。
- `rx_notify_does_not_exit_batch_without_imsic` — 断言 IMSIC 未占用外部中断线路时退出
  原因为 `TIMEOUT` (即未为 RX 通知退出), 锁定上述门控。

## 飞地保存侧改读本次陷态的 mstatus 判定 FS: 跨时间片的浮点寄存器不再被清零

### 现象

`tee_ecall_regress` 的 `ising` 载荷在飞地内算出错误的物理量: 低温 `T=1.0` 的磁化强度
报 `|m| = 0.0489` (铁磁有序应接近 1), 且该载荷自检行
`[PASS] ordered at low T, disordered at high T` 不出现。同一个二进制不经飞地执行
(`qemu-riscv64` 原生, 或 pyremu 单进程直跑) 时 `T=1.0` 得 `|m| = 0.999388`, 与原生结果
逐位一致 — 故障只出现在飞地的时间片切换路径上。

### 根因

M 模式飞地管理器 SUSPEND 时经 `save_enclave_ctx` 保存飞地上下文。修复前其调用顺序为
GPR、FPR、CSR, 而 `save_fpr_for_enclave` 用 `ctx->mstatus` 的 FS 字段判断 "FPR 是否有
未保存的修改"; `ctx->mstatus` 的唯一写入者却是排在 FPR 之后的 `save_csr_for_enclave`。
于是保存 FPR 时读到的是**上一次**切出时的旧值: 飞地首次切出时它是 `init_enclave_ctx`
写入的 `FS=Initial` (0x2000), 判定 "无需保存" 而直接返回; 随后 `save_csr_for_enclave`
才把 `ctx->mstatus` 整体覆盖为本次陷态携带的 `FS=Dirty`。

恢复侧 `restore_fpr_for_enclave` 见 `FS >= Clean` 便认为副本有效, 用 `ctx->fpr` — 建
飞地时 `sbi_memset` 清零的数组 — 覆盖飞地正在使用的全部 32 个浮点寄存器。此后每个时间片
的 SUSPEND/RESUME 都会重演同一过程, 故飞地内**任何跨越一次时间片的浮点中间结果都会
归零**。

ising 的 Metropolis 接受判据 `rng.gen::<f64>() < (-de * beta).exp()` 每次迭代都读浮点
寄存器; 从恢复点起判据左侧恒为 `0.0`, 翻转判决被系统性偏置, 各项累加统计量 (se、se2、
sm、sm2、sm4) 也自恢复点重新起算, 最终 `|m|` 由 0.9994 塌到 0.0489。

### 修复

`bsp/custom-opensbi/lib/enclave_ext/enclave_mem_state.c`:

1. `save_fpr_for_enclave` 改以本次陷态保存的 `regs->mstatus` 判定 FS (`regs` 为空时回落
   到 `ctx->mstatus`), 使该函数与调用顺序解耦。
2. `save_enclave_ctx` 的调用顺序改为 GPR、CSR、FPR。FPR 保存末尾会把 `ctx->mstatus`
   的 FS 由 Dirty 改写为 Clean (表示 FPR 已落盘), 该改写必须发生在
   `save_csr_for_enclave` 整体覆盖 `ctx->mstatus` **之后**, 否则会被丢弃。

两处改动互补: 前者去掉对调用顺序的隐式依赖, 后者保证 "FPR 已落盘" 这一标记能留存到
下一次切出。

### 回归测试

以 `fn_apps/ising` 作为跨时间片浮点状态保持的端到端见证 — 该载荷计算密集、每次迭代都读
浮点寄存器, 总迭代量跨越多次时间片:

- 修复前 (`/tmp/regress_diag.txt`): `T=1.0` 的 `|m| = 0.0489`, 自检 `[PASS]` 行不出现。
- 修复后 (`/tmp/regress_fpr.txt`): `T=1.0` 的 `|m| = 0.9994`, 自检行
  `[PASS] ordered at low T, disordered at high T` 出现; 扫描点 `T=1.80` 的
  `E/N=-1.860 |m|=0.957 C=0.4606 chi=0.1167 U4=0.6655` 与 `qemu-riscv64` 原生参考一致。

### 附: 时间片长度实测

排查期间以 `make -C bsp/sittim DIAGNOSTIC=1 build` 打开运行时诊断输出,
`[quota] suspend t=<mtime>` 相邻两次的间隔实测为 10,013,000 mtime tick, 与设计值
`TIMER_INTERVAL (10000) x TIME_QUOTA (1000)` 一致; 按每 tick 5 条指令
(`NS_PER_INSTR = 20ns`, 时基 10 MHz) 折算, 一个时间片约 5.0e7 条指令。

## 2026-09-12 — UART 寄存器字段随设备状态同步到持久 FFI 上下文: 快速输入不再冻结

### 现象

交互式控制台下快速键入/粘贴 (连续若干次瞬时灌入约 100 字节) 后, 宿主 CPU 占用飙升
且模拟器长时间无响应; 期间 Ctrl+Q 仍能退出。进程内探针 (/tmp/freeze_core.py) 采样
到的冻结指纹稳定复现 (40+ 次采样, 约 10 秒无任何指令推进):

```
notify=1 ring=170 fifo=32 ie=0x02 ip=0x03 txc=0x10001 ext=1 plic=10
```

回溯显示 hart 0 位于 PLIC 中断服务路径 (`plic_handle_irq` -> `handle_irq_event` ->
`nbcon_device_release`), hart 1/2 在空闲路径自旋等待时钟基锁。

### 根因

`FfiUartCtx` 的 `ie/txctrl/rxctrl/rx_fifo_len` 是加速执行引擎内联应答 guest 寄存器读
(IP/IE/TXCTRL/RXCTRL) 的数据源, 而修复前该结构由 `_native_marshal_uart` **每轮重新
构建** 为一次性快照。batch 运行期间 RX daemon 线程把新字节填入 RX FIFO 时, Rust 侧
读到的仍是本轮的 marshal: FIFO 当时为空 (`rx_fifo_len=0`, `rxcnt=0`), 于是
内联应答 `IP` 返回 rxwm=0。Linux 的 `sifive_serial_irq` 据此判定无接收数据, 直接返回
而不读 RXDATA。

RX 中断因此永不被清除: UART 的 PLIC 源电平保持为高, guest 反复 claim/重入 —
中断风暴。CPU 被中断服务程序占满, 其它 hart 饿死在时钟基锁上; 而 guest 不读
RXDATA 使 FIFO 恒满 (`fifo=32`), `drain_rx()` 在 `can_rx()` 处提前返回, ring buffer
积压 (`ring=170`), 输入再无回显。整轮只能在看门狗超时后才结束, 故表现为长时间冻结。


### 修复

UART 设备持有一个 **持久** `FfiUartCtx` (`UART._ffi_ctx`, 由 `Emulator` 在
`_init_for_speedup_lib` 创建并注入), 并在 `_publish_native_regs()` 中把

## 2026-09-10 — 首次 sret 前清 sstatus.SIE: 飞地载荷不再被预 arm 定时器中断击穿现场

### 现象

tee_ecall_regress 的每个 fn_apps 载荷都报 `load <name> (exited-err): FAIL`, 且全程
无任何 `[sys]` 系统调用行: 载荷一条指令都未执行即自毁为 EXITED_ERR (退出码 139 =
128+SIGSEGV)。`[trap] u-fault scause=0xc stval=0x8300445a sepc=0x8300445a` —
U 模式在运行时自身的物理地址 0x8300445a 取指, 触发取指页错误。

### 根因

`rust_main_after_mmu` 末尾写入待进入 U 模式的现场 (sepc / sstatus / sscratch) 时,
`sstatus.SIE` 仍为 1。而 `sbi_set_timer(now + TIMER_INTERVAL)` 在 ELF 加载**之前**
就已 arm, 到函数末尾时 deadline 早已过期、STIP 已挂起。一旦末尾 `csrw sie` 打开
STIE, 该定时器中断立即在之后的指令处被取走。陷态入口的硬件行为: `sepc ← 被中断的
物理 PC` (运行时自身, 0x8300445a)、`SPP ← 1`; 而 handler 的 `sret` 返回后按 xRET
规则把 `SPP` 清 0。于是首次 `sret` 便以 U 模式在运行时自身的物理地址取指, 恒等映射
页无 U 权限, 立即触发取指页错误 — 载荷一条指令都未执行。

证据链: M 模式探针捕获到 `[mdbg] redirect eid=17 cause=0xc mepc=0x8300445a prv=0`
(取指页错误从 S 模式重定向, mepc 恰为运行时物理地址), 与 S 模式
`[trapdbg] n=1001 scause=0xc sepc=0x8300445a` 一一对应; 且该 STI 中断在窗口内循环
投递约 1000 次 (mepc 反复落在 0x4a94/0x4bd6 两处 ecall), 确认是定时器中断击穿了
现场写入窗口。此前「M 模式重定向覆写 sepc」的假设被排除 — 根因是 S 级中断, 非 M
模式。

### 修复

在 `rust_main_after_mmu` 写入现场前追加 `sstatus &= !csr::SSTATUS_SIE`, 使现场写入
与 `sret` 之间不可被 S 级中断打断 (与 `finalize_switch` 在 SIE=0 的 trap 上下文里
写 sepc/sstatus 的不变量一致)。SIE 经 `sret` 由 SPIE=1 恢复, 载荷运行时的定时器
抢占与 host IPI 不受影响。验证: 新二进制 `andi a0,a0,-0x103` (同时清 SPP 与 SIE,
旧为 `-0x101` 仅清 SPP)。

### 复跑与观测

重编 + 重部署 fw_jump.elf 后, `[sys]` 行首次出现 (载荷执行 musl 启动 syscall:
set_tid_address/brk/mmap), 确认载荷已真正转入运行。但因载荷计算速度问题 (见
Task 1, cfrac 分解 19 位合数在模拟器内耗时远超时间片预算), 尚未跑到 summary。

## 2026-09-08 — 飞地运行状态经 a1 通道显式返回: tee_ecall_regress 判定可信化

### 现象

tee_ecall_regress 对每个 fn_apps 载荷都报 `load <name>: PASS`, M 侧 mem-interact
报告也恒为 `alloc_denied_req=0`, 但实际许多载荷是在一个时间片 (TIME_QUOTA) 耗尽后
被 M 模式终止的。PASS 与真实执行状态脱节, 不可信。

### 根因

驱动 ENTER/RESUME ioctl 把一切交还 (挂起、自退、被终止) 都折叠为返回值 0, 工具把
`rc == 0` 当成「干净跑完」; `alloc_denied_req=0` 只说明载荷未触发扩容被拒, 与是否
跑完无关, 却被引用为正常证据。

### 修复

1. 运行状态契约: M 侧 ENTER/RESUME 返回时经 a1 写入运行状态枚举 (与用户态
   tee_enclave.h 两份的 enum tee_run_state、M 侧 ext_ecall.c 的 ENCLAVE_RUN_* 对齐):
   SUSPENDED=0 存活挂起 (host 应 RESUME 继续); EXITED=1 自毁退出且退出码 0;
   EXITED_ERR=2 自毁退出但退出码非 0; ABORTED=3 越界被 M 强制终止; HOST_KILL=4
   host 请求终止。越界终止无条件折算 ABORTED, 故障地址不再被当作退出码。
2. 驱动 ENTER/RESUME 以该枚举作为 ioctl 返回值: rc >= 0 即运行状态, rc < 0 为调用
   期失败 (-errno), 载荷未被转入运行。
3. M 侧 [dbg-mem-interact] 报告按终止路径标注 term: self-exit / host-shutdown /
   fault-abort, 越界终止不再误标 self-exit。
4. 全部 ENTER/RESUME 调用方按新契约改写: 新增运行辅助 run_till_norm_done
   (ENTER + 至多 RESUME_BUDGET 次 RESUME, 直到离开 SUSPENDED); 原「==0 即成功」
   语义改为 rc >= 0 / rc < 0。涉及 tee_ecall_regress / tee_test / tee_malice /
   tee_concurrent / cross_enclave_cache / random_victim_loader。
5. tee_ecall_regress: load 判定 PASS 仅在权威自退 (TEE_RUN_EXITED) 时成立, 其余形态
   据实标 suspended / exited-err / aborted / host-kill / enter-failed 并 FAIL;
   mem_pool 连续性断言只在 ENTER 返回 rc < 0 (真被拒) 时判碎片化, 排除自退等合法
   让出。

### 复跑与观测

- host 构建 (均已重编通过): cache-probe-exploit 下 `make all`
  (riscv64-linux-gnu-gcc -static); 顶层 `make build-fw-jump`; 
  `linux-driver/build-driver.sh` (需 bsp/linux 已构建)。
- guest: 模拟器引导进 shell 后 `cd /eval/cache-probe-exploit && make regress`。
- 工具侧 [regress] 输出: `load <name> (<term>): PASS/FAIL`, 仅 term=exited 的 PASS
  可信 (自毁退出、退出码 0); mem-oom-rejected (连续 32 次 CREATE 失败判池耗尽);
  mem-contiguity (ENTER 仅在 free_total < 2 时才允许被拒, first-fit 分配器回归红线);
  mem-shutdown-freed / mem-reusable; `summary: ALL PASS`。
- M 侧串口在槽位回收时打印 `[dbg-mem-interact] enclave_id=.. term=.. alloc_req=..
  alloc_denied_req=.. free_req=..`; term=self-exit 应对齐工具侧 (exited),
  term=fault-abort 应对齐 (aborted)。alloc_denied_req=0 只证明扩容无被拒, 不能
  证明跑完。

### 回归红线

1. 工具标 (exited) PASS 同时 M 侧同飞地 term=fault-abort: 越界终止又被折算成自退。
2. mem-contiguity FAIL: first-fit 被改回中心放置, 或 ENTER 拒绝条件误判。
3. 载荷时间片耗尽挂起却被标 PASS。

## 2026-09-05 — S 模式载荷加载 bss 清零穿写共享扁平页: musl 静态常量被误释放

### 现象

TEE 飞地运行 `fn_apps/bin/cfrac` (musl-static 载荷) 时, 载荷在 `free()` 内部
`get_meta` 断言处触发 `sb zero, 0(zero)` store fault 崩溃 (U pc 0x1ac4e)。
U 模式运行约 1.07 亿条指令后稳定复现, 与被释放地址落入 `.data` 头部
(`pzeroConst` 静态常量) 相关。

### 根因

S 模式运行时 `sittim` 的 `map_one_segment` 只把载荷 ELF 各 PT_LOAD
的文件页映射到 M 模式移交的扁平拷贝 (map 只映射、不复制文件字节)。
cfrac 的 LOAD#3 (`.relro`, filesz 0x140) 与 LOAD#4 (`.data`) 共享文件偏移
0x12000 的那张扁平物理页: 前者段尾与其 bss 同页, 后者把同一物理页映射到另一段
U VA。LOAD#3 的 filesz 未页对齐 (段尾 0x242d0) 且 memsz 大于 filesz, 其 bss
清零 `write_bytes` 覆盖 [0x242d0, 0x25000), 穿写共享扁平页, 抹掉 LOAD#4 的
`.data` 文件头 (含 `pzeroConst` 的引用计数字段, 被置 0)。musl atop 堆在平衡时把
该静态常量判定为待释放, 走 `free` 后 `meta->mem != base` 断言失败。

### 修复

`bsp/sittim/src/elf.rs` — `map_one_segment` 在 bss 清零前先把末张
文件页私有化: 当 `p_vaddr + p_filesz` 非页对齐时, 分配一页、从扁平拷贝复制本段
文件前缀, 再把该 U VA 页重映射到私有页; 随后的 `write_bytes` 只落在私有页上,
扁平拷贝保持原样, 后续 LOAD 段复用的文件字节不再被抹掉。

### 验证

- 字节探针: U 入口读回 `pzeroConst` 与 ELF 文件字节一致 (修复前为全零)。
- 完整运行: 修复前约 1.07 亿条指令处 abort; 修复后越过原崩溃点, 持续运行至
  载荷结束 (约 13 亿条指令, 无 abort)。

## 2026-09-01 — `csrw sip`/`csrw mip` 覆写硬件只读位: 飞地回归后输入冻结

### 现象

`make emu-linux-sh` 引导 Linux 到 zsh shell 后运行 `regress.sh` (TEE 飞地
CREATE/ENTER/SUSPEND/RESUME/SHUTDOWN 回归), 测试完成之后键盘输入不再到达 guest
shell (输入冻结), 但 Ctrl+Q 仍可退出模拟器。所有 hart 的 mip 均变为 0, 挂起的
SEIP (PLIC 外设中断) 与 STIP (SSTC 定时器) 被清掉, UART RX -> PLIC -> SEIP ->
WFI 唤醒链断裂。

### 根因

RISC-V 规范中 `sip` (0x144) 是 `mip` 的只读视图: **唯一可写位是 SSIP (bit 1)**,
STIP (bit 5) 由 SSTC 定时器、SEIP (bit 9) 由 PLIC 硬件独占。这与 `sie` 不同 —
`sie` 可写所有 mideleg 委派位 (对称视图), 但 `sip` 不是。此前的实现把 `sip` 写
与 `sie` 写对称处理 (`mask = mideleg`), 使 `csrw sip` 能覆写 STIP/SEIP。飞地
上下文切换 `restore_csr_for_enclave` 执行 `csr_write(CSR_SIP, saved_sip)` 写回
陈旧的 sip (STIP/SEIP 位为 0), 每次 ENTER/SUSPEND/RESUME 都把挂起的中断位清零,
regress.sh 反复调用后 SEIP/STIP 永久丢失。Python 侧 `write_csr` 的 `mip` (0x344)
写亦无只读位屏蔽 (native `MIP` 写已正确)。

### 修复

`csrw sip` 只允许写 SSIP (bit 1), 保留 STIP/SEIP; Python `csrw mip` 补上与
native `MIP` 写一致的只读位屏蔽 (MSIP/STIP/MTIP/SEIP/MEIP)。

- `pyremu/_native/cpu/src/csr.rs` — `SIP` 写由 `mask = mideleg` 改为 `wr_mask = 1 << 1`
- `pyremu/core/hart.py` — `write_csr` 的 `sip` 分支改为仅写 SSIP; 新增 `mip` 分支
  加入只读位屏蔽 (`ro_mask = (1<<3)|(1<<5)|(1<<7)|(1<<9)|(1<<11)`)

### 回归测试

- `write_sip_preserves_stip_and_seip` (Rust) — 委派 STIP/SEIP/SSIP 后 `csrw sip, 0`,
  断言 STIP/SEIP 保留、SSIP 清除 (修复前 `mask=mideleg` 会全清)
- `TestSipMipReadonlyMask` (Python) — `csrw sip, 0` 与 `csrw mip, 0` 两条路径各一例,
  验证硬件只读位不被覆写



### 现象

`make emu-linux-sh` (legacy PLIC, 3 harts, `init=/bin/zsh`) 在
"Run /bin/zsh as init process" 之后仍间歇性停滞 (MSIP 电平保留修复后 2/6 次),
180 秒以上无新输出, 且停滞进程无法被 Ctrl+Q 终止。GDB 挂附显示停滞进程仅剩
5 个线程: main (阻塞在 `run_parallel` 的 join)、1 个 hart 线程 (阻塞在 glibc
`syscall` futex)、termio 轮询线程与 2 个 Python 轮询线程; 软件看门狗与另外
2 个 hart 线程均已退出。看门狗只在 stop/超时时退出 (1800s 超时排除), 故
`stop_flag` 必然已置位。

### 根因

`wfi_spin` 停驻的 hart 用无限 `std::thread::park()` 阻塞, 唤醒完全依赖外部
unpark: 看门狗每 5ms 周期 `unpark_all_harts`、其他 hart 退出时的完成信号
(`run_harts` 的 exit-closure)、MSIP 发送方。当某 hart 在最后一次 unpark 之后
park、且看门狗已按 stop 退出时, 该 hart 会带着已置位的 `stop_flag` 永久睡眠:
无人再 unpark, `run_harts` 的 join 永不返回, batch 永不收敛, Ctrl+Q 也因
main 卡死在 FFI 调用内而无法生效。全 crate 枚举确认 `wfi.rs` 的 `park()` 是
唯一无限阻塞点: 所有 `Mutex::lock` 均以 `if let Ok` 不阻塞, 唯一 `.unwrap()`
的 `SH_LAST_TAGGED_HART` 仅在 semihosting 路径 (Linux 启动不使用)。

`wfi_spin` 的无限 `park()` 改为与看门狗轮询周期对齐的自醒阻塞
`park_timeout(WATCHDOG_POLL_US)` (5ms)。外部 unpark (MSIP 发送方/看门狗) 仍
提供零延迟唤醒; 即使全部外部唤醒源消失, 停驻 hart 也会自行醒来重新检查
`stop_flag` 与中断挂起 (mtip/msip/imsic/ext_irq/uart_rx), 有界时间内必定
收敛退出。自醒周期与看门狗现有 5ms 周期唤醒等价, 正常路径零额外开销, 仅在
看门狗消失后兜底 — 将批次终结正确性从"4 线程 unpark 时序无竞态"变为
"每 hart 独立自愈"。

- `pyremu/_native/cpu/src/interrupt/wfi.rs` — `park()` 改为
  `park_timeout(WATCHDOG_POLL_US)`; 更新设计注释 (自醒安全网)
- `pyremu/_native/cpu/src/concurrent.rs` — `WATCHDOG_POLL_US` 改为
